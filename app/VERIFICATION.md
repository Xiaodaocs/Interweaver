## 1. 运行方式

```bash
cd app
node server.mjs          # → http://localhost:5188（静态；根路径 302 到 /login.html）
node server-api.mjs      # → http://localhost:5189（后端 API + SQLite 用户系统；可选，离线也能用画布）
```

浏览器打开 **http://localhost:5188**（导航栏右段的 `?` 打开分 P 验收清单，可勾选，进度存在本地）。

```bash
npm test             # 纯逻辑单元/集成核验（最近一次实测 138 项）
npm run test:e2e     # 真实 Chromium 端到端核验
npm run test:layout  # 布局/命中/像素核验
npm run test:visual  # 视觉核验：读画布像素证明"点更醒目""圆自带直径"等
npm run test:perf    # 性能验收：画布 + 曲线采样
npm run stop         # ★ 先让 5189 空闲（见下）
npm run verify       # 全部（外壳会自己在 5189 起测试后端，跑完关掉）
```

★ **`npm run verify` 的前置条件是 5189 空闲**：外壳 `tests/verify-with-api.mjs` 要独占 5189 起一个
**自带临时库 + 临时日志**的测试后端，端口上已经有人在跑就**直接拒绝运行**（`exit 1` + 人话），绝不复用
（这条纪律来自两次实测事故：老的"端口上有人就复用"写法把 `tel_*` 测试账号写进了用户的真实库）。
单项检查（`check-api` / `check-account-isolation` / `check-telemetry` …）都**自带独占端口 + 独占临时库**，
不受这条影响 —— 守卫是 `tests/_own-backend.mjs`：身份判据 = 后端 `/health` 回显的 `log` 路径必须等于
本检查自己传进去的那个临时日志；真实后端恒为 `data/api.log`，永远对不上。

**核验套件的稳定性**：所有浏览器套件都加了 `--disable-background-timer-throttling` 等参数，并且不靠 `setTimeout` 猜渲染时机——视觉套件改为**轮询画布像素直到特征出现**。原因：headless 下 rAF 会被节流，固定 sleep 会造成随机失败（这个坑实际踩过一次：同一套件单独跑通过、连跑就失败）。修好后连续三轮全量核验结果完全一致。

## 3. 核验中发现并修复的真实 bug

自动化核验的价值在这几个 bug 上体现得最明显——它们都只在真实浏览器里才暴露：

| # | Bug | 影响 | 根因 | 修复 |
|---|-----|------|------|------|
| 1 | **验收清单永久遮挡右侧面板** | 面板几乎不可点击，"?"按钮看似失效 | `#checklist { display: flex }` 压过了 `[hidden]` 的 UA 默认 `display:none` | `styles.css` 加全局 `[hidden] { display: none !important }`，并把清单移到面板左侧（右 352px）避免重叠 |
| 2 | **右键菜单「关联…」和「删除」必然抛异常** | P5 核心入口完全不可用 | `close()` 先把 `currentEnt` 置空，随后又读 `currentEnt.id` | 先取 id 再 `close()` |
| 3 | **ƒx 表达式草稿被面板重绘清空** | 输入 `y=a*x+b` → 点"建滑杆"芯片 → 表达式消失，用户得重打 | 芯片点击触发 `structure` 事件 → 面板整块重绘 → input 新元素无值 | 草稿存入 `fxDraft.text`，重绘时回填并重新解析 |
| 4 | **预设拖放永远落在画布中心** | 拖到哪都放到中间，"拖出来"的直觉失效 | `setPointerCapture` 使 `e.target` 恒为预设项，`overDock` 判据恒真 | 改用 `elementFromPoint` 判定落点，拖到画布才放置、落在面板上视为取消 |
| 5 | **框选一个也选不中** | Ctrl 之外的多选路径等于失效 | 屏幕 y 向下、世界 y 向上；`s2w(min sx, min sy)` 得到的是左上角（世界 y 最大），导致 y 区间判据恒为空 | 取出两角后对 x/y 各自重新取 min/max 归一化 |
| 6 | **多选后拖动只移动被抓住的那一个** | "画个三角形整体挪走"做不到（P2 验收项） | 拖动逻辑只处理单个实体 | 各实体新增 `translate()`；多选抓本体时整组按位移平移（相对位置不变） |
| 7 | **自动组合出的多边形是"蝴蝶形"** | 面积恒为 0 或只剩一半 | 回路的末节点就是起点（闭合点），却被当成独立顶点，导致 `v1 == vn` 退化 | 顶点取 `[na, nb, ...path.slice(0,-1)]`，去掉闭合点；单测断言面积 6 / 15 |
| 8 | **多边形/圆弧读不到宿主参数（`env.val is not a function`）** | 悬停、框选、拖动全部报错 | ① `polygon.hit` 少写 `cam` 形参，`env` 收到了 `cam`；② 绘制上下文与取值环境曾是两个不同对象；③ 框选调用 `features` 漏传 env | 统一把取值环境（含 `val/ent/st`）直接当作绘制/命中上下文传递；补齐 `polygon.hit` 签名；框选补 env |
| 9 | **圆弧端点把手挡住底下的线上点** | 看着有个点却拖不动 | 命中测试只按"后画的在上"，圆弧后画即抢走点击 | 命中优先级改为"可拖的优先于只能选的"，再退回最上层 |
| 10 | **视觉核验套件时好时坏**（单独跑通过、连跑失败） | 核验结论不可信 | headless 下 rAF 被节流，套件用固定 `setTimeout` 猜渲染时机；采样到的是上一帧 | 浏览器加反节流参数；改为**轮询画布像素直到特征出现/消失**再断言（差分测量而非绝对阈值） |

另外补了两条守边界的单测：**三笔共线不算三角形**（面积≈0 时不组合，避免"随手画三笔却说你是三角形"）、**自动组合可一步撤销**（撤销恢复三条线段，重做又变回多边形）。

此外修掉若干测试自身的期望错误（链长差 1、清单条目数、favicon 404 噪声、拖动过滑杆后仍假设 a=2、顶点序号假设）——这些是核验脚本的问题，不是产品代码。

## 3.5 用户报告问题的修复记录（本轮）

| 用户报告 | 根因 | 修复 | 核验证据 |
|---------|------|------|---------|
| **① 网格只能左右移动、横轴在格线间跳动** | **同一个根因**：竖线从"世界坐标 step 整数倍"起算（正确），横线却从**屏幕底边的世界 y** 起算（未吸附）。于是横轴被画在"离 0 最近的那条生成线"上，随平移整格跳动；横线族相对世界坐标持续偏移，又因线彼此同形，纵向平移时网格看起来完全不动 | 抽出纯函数 `gridLines(cam,w,h)`：横竖两族都用 `i*step` 生成，坐标轴严格等于 0；刻度文字按步长取整（`formatGridValue`） | 单测：任意相机位置下所有线与 step 整数倍误差 <1e-9、轴精确为 0、连续平移时轴屏位位移恒等于理论值、刻度不出现怪值；**e2e 像素级**：抽取屏幕竖条最暗行作为横轴位置，与理论值最大偏差 ≤2.5px（修复前会整格跳约 40px） |
| **② 封闭图形需自动组合为一个整体** | 原本没有"组合"概念，三条线段就是三个独立对象 | 新增 `polygon`（顶点数任意，`v1x…vny` 动态参数）+ `detectClosedShape()`：端点在容差内聚类成节点，DFS 找回起点的简单回路，把参与的线段合并为一个多边形（顶点取聚类均值，保证严格闭合） | 单测 8 项：三角形面积 6 / 周长 12、矩形面积 15、开放折线不误组合、容差 0.1 也能识别、整体平移与单顶点拖动；**e2e**：真实点三笔围成三角形 → `polygon=1, 剩余线段=0`，拖顶点面积随之变化，并弹出「已自动组合为三角形」 |
| **② 点工具可"截"出圆弧/线上点** | 点只能落在自由坐标上，无法贴到已有图形 | 新增 `edgepoint`（参数 `t` 可绑定，位置由宿主几何派生）与 `arc`（宿主圆 + 两个线上点，取较短弧）；点工具点击图形边/曲线即生成线上点，圆上第二个点自动截弧 | 单测 6 项：线段/圆/多边形投影与参数化、90° 弧长 4.712、半径×2 弧长×2、角距缩到 30°、宿主删除后不抛异常；**e2e**：真实点击圆上两点 → 弧 90° / 4.712、拖点变 45°、线上点始终精确贴圆（偏差 <1e-6）、点圆内部仍是自由点 |
| **② 点不显眼** | 4.5px 实心点直接压在网格线上，对比度低 | 自由点：纸色底垫（r=7）+ 实体色芯（r=5）+ 白描边；线上点：空心环＋中心点（"贴着线"的语义）；多边形顶点始终绘制 | **视觉套件读像素判定**：芯宽 9px；±6px 处与"无标记"基线差异 33（证明底垫把坐标轴盖住了）、±11px 处差异 0（证明影响范围约 7px）；线上点内部比环亮 71（确实是空心环）；顶点未选中也可见 |
| **③ 预设库的圆/单位圆不能用且重复** | 单位圆被 `fixedPos` 钉在原点——用户若已平移到别处，放下后"看不见"，表现为"点了没用"；圆本身也与工具栏重复 | 按建议**删除这两个预设**（现为 正弦/余弦/抛物线/三角形/正方形）；工具栏的圆**自带直径线段**（直径＝拖动条：抓它平移圆，抓两端改半径），新增派生量「直径 2r」 | 单测：预设列表断言不含圆/单位圆、直径派生量 = 4；**e2e**：抓直径拖动使圆整体平移（圆心 y 0→2.00，半径不变 3.00）、预设库文本不含圆/单位圆 |

### 本轮发现并修复的 bug

| # | Bug | 影响 | 根因 | 修复 |
|---|-----|------|------|------|

## 3.8 下一阶段开工：P7 反向求解（拖图形 → 变量跟着动）

> 路线图 P7。这是产品最初描述里的核心魔法："我摁住并拖动这条线，a 的参数（包括滑杆）也会变动，从而与之关联的正弦波也会动"。

| 档位 | 判定 | 行为 |
|------|------|------|
| ① 解析反解 | 表达式对上游符号可线性化（`linearize()`：`a`、`a/2+1`、`9a`、`-3k+10`、`c1.r*a`…） | 直接 `x = (目标 − b)/a`，精确、一次到位 |
| ② 数值反解 | 单源但非线性（如 `sin(a)*5+6`） | 牛顿迭代 + 多初值，**取离当前值最近的收敛解**保持分支连续 |
| ③ 弹簧回弹 | 多源（`a+b`）或确实无解 | 图形先跟着指针被"拉开"，松手弹回原值，并提示"这个参数正由「…」驱动" |

**写回上游**：源是变量 → 写变量值（**尊重 min/max，越界钳制**并标记）；源是另一个实体的参数 → 若它本身也被绑定则**递归反解**（`how` 记为 `analytic>analytic` 这类链），否则直接写参数。

## 3.11 八项修改：角度实体 / 参数显示 / 菜单与窗口（含两处根因）

### ⑥ 水平/竖直"飞走变歪"——根因（已定位并修复）

`app/src/tools.js` 里 `const patch = fn(...)` 声明在 `if (fn) { … }` **块内**，而"钉住正在拖动的参数"的代码在这个块**外面**：

```js
} else {
  if (fn) { const patch = fn(...) || {}; … }   // ← 块级作用域
}
const pinKeys = new Set();
if (typeof patch !== 'undefined') …            // ← 恒为 undefined → pin 恒为空集
S.ensureEvaluated(st, { solve: true, pin: pinKeys });
```

后果：求解器把**被拖的端点也当成自由变量**，水平/竖直约束的修正被平摊到两端 → 每帧"设 y2=指针，再把 y1、y2 一起拉向均值"，于是被抓住的一端追不上指针、另一端反向乱跑，快速拖拽时线最终变歪、看起来"飞老远"。
（早先探针的数字正是这个公式的指纹：指针在 y=3.0，线段却停在 y1=y2=2.63。）

**修法**：改为在能拿到 patch 的作用域里收集 `movedParams`，保证 pin 始终是"本次真正改动的参数"；再给水平/竖直加**解析前置轮 + 收尾轮**（`axisPass`），优先改没被钉住的那一端、两端都不可动时改"非主导端"，让约束优先于拖动的冗余自由度。

### ⑤ 裁切段"仍像宿主那样变姿态 / 都叫圆弧"——双根因

1. `tools.js` 的提示**写死** `已截出圆弧`，任何宿主都这么说 → 改为按来源说人话（正弦段 / 抛物线段 / 弧段 / 线段…）；
2. 截出来的 `curvepiece`/`arc` **每帧从宿主重新采样**（且 `drag.body = null`，根本拖不走）→ 改为 `materializePiece()`：截出来就是**独立解析实体**（圆→自由圆弧、正弦→带定义域正弦、抛物线→带定义域抛物线、函数图→同表达式收定义域、线段→线段、自由曲线→取点子段），带 `piece / fromLabel` 出处标记；`func` 补了 `cy` 参数与本体拖动，于是各段都能整体平移而姿态不变。

### 性能判据的更正（重要，请知情）

`perf-check` 原先用"帧率 ≥ 25"作为判据。本轮用三层测量证明**该判据在 headless 下测不出应用成本**：

1. **消融矩阵**（同一 1000 实体场景）：基线 3 次 10.5/10.6/10.6；关参数标签 10.6；关成就运行时 10.6；两者都关 10.6 —— 与加载内容无关；
2. **实体数缩放**：1000→15.1、600→10.5、300→10.0、120→9.9、40→9.9 fps —— **只剩 40 个实体仍 9.9 fps**，说明是固定节拍（headless rAF 节流约 10Hz）；
3. **直接量单帧绘制**（新增诊断钩子 `__IW.renderOnce()`）：1000 实体 **3.7ms/帧（≈270fps）**、600→2.4、300→1.3、120→0.5、40→0.2ms —— **应用本身很快**。

因此判据改为**单帧绘制耗时 < 16ms**（实测 4.9ms，具备 60fps 能力），帧率降级为信息输出并保留 ~10fps 的合理性下限。**这不是放宽阈值，而是换成一个在该环境下可辩护的量**，依据写在 `tests/perf-check.mjs` 的注释里。
