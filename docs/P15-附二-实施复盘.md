## 一、走线降交叉：三次失败 → 曲线一次成功

| 尝试 | 交叉数（基线 57） | 结果 |
|---|---|---|
| C1-a 车道单调分配 | **63** ✗ | 且穿线 0 → 4 ✗，已回退 |
| C1-b 层内 median 重排 | **90** ✗ | 已回退 |
| P2 主干道（长边走全图顶部） | **67** ✗ | 且破一条硬要求，已回退 |
| **A 长边曲线化（跨 ≥3 层改三次贝塞尔）** | **20** ✓ | 曲线占比 19%，硬要求全绿 |
| 叠加组间留白与容量调整后 | **27** | 曲线 27%（上限 35%） |

**关键数据（`diag-crossings.mjs`）——为什么前三次必然失败：**

```
跨1层 21 条边 →  0 处交叉
跨2层 11 条边 →  3 处
跨3层  8 条边 → 12 处
跨4层 15 条边 → 32 处   ← 最大头
跨5层  7 条边 →  7 处
跨6层  2 条边 →  3 处
长边（跨 ≥3 层）贡献 = 54/57 = 95%
```

**结论**：交叉是"**长边**"造成的，而前三次尝试都在**同一个几何体系内换位置**（改次序 / 改车道 / 挪到主干道），
所以只能把交叉搬到别处，消不掉。**换成曲线（换了几何本身）才成功。**

## 二、列间走廊：从"数学上无路"到"6/6 有路"

- 起点：`走廊 = COL_W(216) − (NODE_W150 + 2×抖动25.9) − 2×padding8 = −1.84px` → **竖直走线无路可走**；
- 实测（`diag-corridor.mjs`）：6 对相邻列走廊全为负（−82 … −324px），跨列矩形重叠 **190 对**，
  **列内节点距列心最大偏差 281px**（抖动上限只有 31px，超 9 倍）；
- 根因：松弛中"排斥力是常量、锚定回拉只有 8%/轮" ⇒ 平衡位移 `f/0.08 ≈ 275px`（与实测 281 吻合）；
- 修法：① 每轮松弛后把 x **夹回抖动边界**；② 抖动上限 12% → 6%（12% 是上限，取下限仍合规）；
- 结果：走廊 101.3 / 62.5 / 50.5 / 50.2 / 57.8 / 85.5px（**6/6 净空为正**），跨列重叠 190 → **0 对**，穿线 **0**。

## 三、三条"设计冲突"（不可同时满足，必须由人拍板）

1. **组间留白 ≥120px ⟂ 曲线占比 ≤25%**：拉开组带 → 长边竖直跨度变大 → 更多边触发曲线回退（19% → 27%）。
   处置：曲线上限调至 **35%**（依据用户指示"实在做不出来就使用曲线"，且 25% 是自定指标）；
2. **带内归属 ⟂ 画布高度**：封顶组带高度 → 画布 3258 → **1127px** ✓，但间距被压到 7.9px ✗。
   根因（`diag-tightpairs.mjs`）：**当前布局的纵向余量是零** —— 最贴边的 15 对全是"同列同组同子道"，dy 恰为 46.0–46.8px；
   → **间距与画布更矮是直接竞争关系**，要同时满足需要一次**全局重排**（不是局部推挤）；
3. **"枢纽密 / 叶端散" ⟂ "层 = 难度"**：枢纽的邻居天然分布在不同层（相距 1–5 列），
   实测"枢纽邻居均距 / 叶端邻居均距 = **2.64**"（要求 ≤0.75）——**几何上不可达**，只能改为视觉权重或取消。

## 四、测试方法的三条教训（都踩过）

1. **能取到 ≠ 取名对**：`fn.parabola.vertex.on.axis` 用了不存在的特征量 `cx`（真名是 `h`，见 `entities.js:1147`）→ 判据永远不成立；
   **规则**：写判据前先在 `entities.js` 查证该实体的 `params`/`derived` 键名（`func`、`derivcurve` 是 `features: () => []`，无法判定，不该写）。
2. **能构造 ≠ 能判定**：`addEntity(st,'tangent',{})` 能返回实体，但**没有 `host` + `p1` 就没有任何特征量** →
   阈值类判据测不了；正确配方：`sine` → `addEdgePoint` → `tangent{host, p1}`。
3. **空数组的 `.every()` 恒真**：我用 `interesting.every(...)` 判断"特征量是否齐全"，空数组直接返回 `true` → 走进错误分支（空真绿灯）✗。
   **规则**：任何"全部满足"的分支判断都必须显式写 `arr.length > 0 &&`。
4. 另外：**逐条改期望是错的修法**。场景表最初用"成立集合 == 期望集合"断言，每加一个正确模式就误报一次
   （连续 4 次）→ 改为"**期望的模式必须成立**"，误报交给专门的反例用例（`mustNotFire`）。

## 六、成就判据的五条"血泪"教训（T8 扩展期间）

成就从 90 条扩到 **134 条**的过程中，判据写错/测试写错共发生 5 类问题，全部记录如下：

1. **键名写错 → 判据永不成立**：「顶点在 y 轴」我写了 `cx`，而抛物线顶点 x 的真名是 **`h`**（`entities.js:1147`）。
   规则：**写判据前先在 `entities.js` 查证 params/derived 的确切键名**。
2. **"参数存放位置 vs 读取位置"不一致 → 派生量全为 NaN**：实体把参数存在 `ent.params`，而派生量 compute 读的是直接属性
   （`ent.host` / `ent.p1` / `ent.expr`）。`semantic.js` 传原始实体 ⇒ 每个 compute 抛错 ⇒ 被 `catch { v = NaN }` **静默吞掉**。
   后果：切线 `m`、割线 `dx`、积分 `err`、`func.expr` **全部读不到**，微积分族 8 条判据全是死判据。
   修法：在 `featuresOf` 里传**扁平视图** `{ ...ent, ...ent.params }`。规则：**"实体在、量却取不到"时，先查参数存放与读取是否一致**。
3. **静默吞异常比异常本身更贵**：`catch { v = NaN }` 让上述问题多花了两轮才定位。规则：**吞异常时必须留下可诊断的痕迹**（至少可选地记录）。
4. **量 ≠ 实体**：「一拖二」我最初按"同一个变量驱动 ≥2 个**不同实体**"实现，但"同一实体的两个参数（A 与 phi）"是两个**量**却只有一个实体 ⇒ 判据名不副实。
   修法：按 **`(to, param)` 二元组**去重（`detail.param` 就在边上）。
5. **构造类 API 的返回值必须检查**：`addProbe(ent,"A")` 返回 `{ error: "没有派生量 A" }`（观察器**只能观察派生量**），
   但我不检查返回值 ⇒ 场景里没有 observe 边 ⇒ 误判"判据不成立"。同类错误此前还出现过两次（`addEntity("tangent",{})`、`addBinding` 用法）。
   规则：**构造失败必须由断言当场暴露**（`ok(pr.ok)`），不要靠"结果不存在"去反推。

另有两条关于**测试写法**的教训：

- **不要逐条改期望**：场景表最初用"成立集合 == 期望集合"，每加一个正确模式就误报（连续 4 次）→ 改为"**期望的模式必须成立**"，
  误报交给专门的反例用例（`mustNotFire`）。
- **空数组的 `.every()` 恒真**：用 `arr.every(...)` 做分支判断必须显式写 `arr.length > 0 &&`，否则会走进"空真"分支（假绿灯）。

## 八、断言设计：三条同源错误（都发生在"观测面"上）

实现正确、断言写错，是这一路最常见的"假红灯/假绿灯"来源。三次错误同源：**观测面选得不对**。

1. **空数组的 `.every()` 恒真** —— 我用 `interesting.every(...)` 判断"特征量是否齐全"，空数组直接返回 `true`，
   于是走进"特征量齐全"的分支（假绿灯）。规则：**任何"全部满足"的分支判断必须显式写 `arr.length > 0 &&`**。
2. **跨状态比大小** —— §11.1 权重断言最初直接取"DOM 里第一个枢纽 vs 第一个叶端"的 `opacity` 比大小，
   但节点的 `opacity` **同时受状态（已点亮/待补/未点亮）影响** ⇒ 我其实在拿"状态"当"权重"比。
   规则：**比较必须在同一状态内进行**（`[data-state="granted"]`）。
3. **未等动画就取计算样式** —— 改成同状态比较后仍不稳：实测枢纽 `opacity = 0.544`，而最终值是 1.0，
   原因是设计 §1.3 的**错相入场淡入**还没结束（浮动动画是 `infinite`，不能用 `getAnimations()` 判空）。
   规则：**测量前先固定时序因素**（等 2.5s 或等动画结束）。

**统一规则**：断言必须选择**与"状态 / 动画 / 时序"无关的观测面**；若只能用受它们影响的量，
就必须先把这些因素固定住（同状态比较、等动画结束），否则得到的红灯或绿灯都不可信。

补充一条工程纪律（也在本阶段踩过）：**提交信息只能描述已验证的事实**。
有一次我先写好"§11.1 完成"的提交信息再跑核验，而核验其实失败了 ⇒ 提交历史里留下了不准确的一句话，
只能在后续提交里更正（`a78198f`）。
